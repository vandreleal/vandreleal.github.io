Building Interactive Pricing Pages with Next.js

June 15, 2024 · 3 min read

Pricing pages sit on the seam between marketing and application. The interactivity expectation comes from the application side: sliders, calculators, dynamic comparisons, live recalculation. The performance expectation comes from the marketing side: fast load, good SEO, minimal JavaScript, no jank on first paint. Whichever side you bias for, you lose on the other.

I built the pricing system for a SaaS product website using Next.js. The logic underneath involved dynamic plan selection, real-time cost calculation, feature comparison tables, and responsive layouts that worked across dozens of plan configurations.

The challenge

The product had multiple pricing tiers across several product lines. Each product had its own plan structure, feature comparison table, and volume-based pricing. Some plans were annual, some monthly. Some had usage calculators driven by sliders. The pricing data came from a CMS.

The goal was a single, composable pricing system that could handle any product’s pricing page without duplicating code.

Dynamic components

I built a set of components that rendered based on CMS data: plan cards, comparison tables, volume discount sections, FAQ accordions, banners. Each section was a modular block the CMS could reorder, show, or hide per product.

The range slider was the most interesting piece. Users dragged to select their expected usage, and the page recalculated pricing in real time. The slider needed custom styling, keyboard accessibility, and smooth transitions between values. Native <input type="range"> renders differently in every browser, so I styled it with CSS custom properties and pseudo-elements.

Plan selection logic

Each product had a different plan structure, with usage-based options that changed the price calculation. The plan button logic needed to know the current plan, the selected plan, whether the change was an upgrade or downgrade, and whether the user was authenticated.

I extracted this into a set of utility functions. The UI stayed simple: one helper returned the button’s attributes, a separate click handler acted on the choice. Business logic stayed testable and separate from presentation.

Comparison tables

The tables needed to be responsive without horizontal scrolling on mobile. I used a grid that collapsed to a stacked format on small screens, with the plan name inline on each feature row so context did not get lost.

Tooltips were CSS-only instead of a JavaScript library, to avoid bundle weight on a marketing page where performance mattered.

What I learned

Pricing pages are marketing pages that behave like applications. They need the interactivity of a dashboard (calculators, dynamic rendering, state management) but the performance expectations of a landing page: fast load, good SEO, minimal JavaScript.
