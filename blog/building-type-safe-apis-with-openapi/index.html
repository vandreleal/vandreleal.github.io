Building Type-Safe APIs with OpenAPI

October 15, 2025 · 3 min read

When multiple product teams ship into the same dashboard against the same upstream APIs, the integration layer is its own product. It has consumers, contracts, and a public surface. The decision that matters is whether to invest in that layer or let each team negotiate API consumption on its own.

The dashboard I worked on had OpenAPI specs already, but nothing generated from them. Every API change meant hand-written TypeScript types needed updating, and integration bugs slipped through to production. The bet was to go all in on OpenAPI as the single source of truth: types, clients, validators, all generated from the spec. The frontend stops defining its own API types.

Three other pieces sit alongside this generation work: contract-first mocks ship the shape before the implementation, a proxy layer unifies two upstream APIs behind one type-safe surface, and a CI pipeline regenerates code and alerts the team on breaking changes. This post covers the generation decision itself.

The pipeline

A codegen step runs on every spec change. It emits TypeScript types, thin client functions, and request/response validators. The first iteration used openapi-typescript for types, with custom templates for the rest. As the validators we needed grew more elaborate, the pipeline later moved to a tool that handles types and Zod schemas in one pass. That migration is its own story.

CI hooks into the spec. When it changes upstream, the regeneration opens a PR. Reviewers see exactly what changed in the contract.

Alternatives considered

The codegen bet rested on rejecting three other approaches.

Hand-written TypeScript types, per consumer. The status quo before this work: each team maintained its own types for the endpoints it called. The synchronization problem this created, types and reality drifting silently, was the reason this work happened in the first place. The cost of leaving it alone was paid every release, not once.

The spec as documentation only. Keep the OpenAPI spec as the agreed contract on paper, but continue to hand-write everything that consumes it. This keeps the spec from gaining teeth: drift surfaces at runtime, not at build time, and the spec stays an aspirational artifact rather than a load-bearing one. A spec without consumers downstream is a wishlist.

Generation, but only for types. A narrower bet: generate the types and keep clients, validators, and request shapes hand-written. This is a half-step that leaves the spec out of the parts that matter most at runtime, where validation, errors, and retries actually live. It also forces the team to maintain two parallel sources of truth: the spec, and whatever the hand-written client believes.

The full-pipeline bet costs more up front but pays back the moment the spec changes. Every alternative has a worst case where the spec drifts from reality. The pipeline forces them back into alignment automatically.

What changed

Integration errors dropped to near zero. Code reviews stopped including manual type-vs-API checks because the pipeline guaranteed them. Refactoring API consumption code became safer; the compiler caught contract violations that previously surfaced in production.

The biggest practical win was confidence. Engineers stopped guessing whether the types matched the response.

What I learned

Codegen is not a silver bullet. The generated code needs to be readable, because if engineers can’t understand the output, they will route around it. I spent time tuning the templates until the generated client felt hand-written.

The other lesson: treat the OpenAPI spec as a first-class artifact. If the spec is wrong or incomplete, the generated code is too. Spec validation in CI fails the build before bad specs reach consumers.
