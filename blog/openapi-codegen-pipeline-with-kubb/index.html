Building an OpenAPI Code Generation Pipeline with Kubb

November 12, 2025 · 4 min read

The dashboard I worked on consumed multiple APIs, all with OpenAPI specs that changed frequently. Keeping hand-written TypeScript types in sync was unsustainable, so I built a code generation pipeline to automate it.

This is one piece of the dashboard’s integration layer. The pipeline is the automation that keeps generated code in sync with upstream specs, and it sits downstream of the contract-first mocks and the type-safe API bet.

Why Kubb

OpenAPI codegen splits along two axes that matter: what gets generated (types only, types plus runtime validators, or a full SDK), and how the output gets customized (none, templates, or plugins). Each axis trades flexibility against ergonomics.

A types-only generator gives clean output but leaves runtime validation as a separate hand-maintained source of truth, which is exactly the synchronization problem the codegen was supposed to solve. A full-SDK generator covers everything in one pass but tends to emit code that does not feel hand-written, and code that does not feel hand-written is the first thing engineers route around when they hit an edge case.

Kubb sits between them. It generates both TypeScript types and Zod schemas from the same spec in a single pass, so the runtime validator and the compile-time type are always derived from the same source. The plugin system was the second piece that mattered: it let me customize the output to match the project’s naming conventions, so the generated client read like something a person could have written. When generated code feels native, nobody wants to fork it.

Preprocessing the Specs

The specs needed cleanup before generation. Upstream services emitted OpenAPI documents that were technically valid but locally awkward: naming conventions varied across teams, optional and required fields drifted, and response envelopes wrapped real payloads differently from one service to another. None of this was wrong. It was the kind of variation that surfaces when each team owns its own spec generation and the consumers converge them later.

I added a preprocessing step that ran upstream of Kubb and normalized the input before every run. The output stayed consistent regardless of upstream wording, which mattered downstream: snapshot diffs only flagged real contract changes, not the cosmetic ones that flipped on each upstream release.

The Automated Pipeline

A CI workflow runs on a scheduled cadence. It fetches the latest specs, runs the preprocessing step, runs Kubb against the normalized input, type-checks the output, and diffs against the previously committed snapshot.

The diff is where the pipeline earns its keep. Three categories matter: added endpoints (mostly safe, but worth flagging in case the addition signals a deprecation elsewhere), removed endpoints (load-bearing breakage, blocks the merge until consumers are updated), and changed shapes (the dangerous category, where same name and different fields is the failure mode that traditionally caught us at runtime).

When the diff turns up changes, the workflow posts a structured summary to a shared channel. Engineers see the changes at the boundary where they happen, not when a build inexplicably starts failing. The summary names the endpoints, classifies each change, and links to the spec revision so the conversation about whether the change is welcome can start with full context.

What I Learned

The pipeline eliminated an entire class of integration bugs. Engineers trust that the generated types match the API contract. Code reviews stopped including manual type-vs-API checks because the pipeline guarantees them.

Codegen pays back only as fast as the regeneration cadence. If the spec changes weekly but regeneration runs monthly, you have bought a delayed integration bug, not a prevention. The scheduled runs were the part that made the bet worth taking. Without them, the same out-of-sync problem returns in a slower form.

The deeper lesson sat one level above the pipeline. The choice of tool is downstream of the choice of source of truth. Once the OpenAPI spec is the source, every tool that respects it is acceptable; every tool that does not is unacceptable. The selection inside the acceptable bucket comes down to ergonomics. Kubb’s was the best fit for this dashboard. For a different shape of project, a different tool might be.
