A Practical Prefetching Strategy with TanStack Query and Router

August 29, 2025 · 3 min read

A dashboard that feels slow loses trust. Users click a navigation link and expect the data to already be there. I built a prefetching strategy that makes a dashboard feel instant, even when the API calls take hundreds of milliseconds.

The work happens in two layers: route-level prefetching in loaders, and intent-based prefetching for the rows a user is likely to click next.

Route-Level Prefetching

I moved from beforeLoad to loader-based prefetching on every route. The loader function calls queryClient.ensureQueryData() with the same query options the page components use. This means the data fetching starts at navigation time, not at component mount time.

The key decision was to use the same query options factory functions in both the loader and the components. I extracted these into domain-specific files so the loader and the component always agreed on cache keys and stale times. By the time the page mounted, the data was already in the cache and rendered without a fetch.

I evaluated defaultPreload: 'intent' for hover-based prefetching at the router level, but turned it off. With loaders already running on navigation and most lists being long, intent-preload was either redundant for the rows we were going to click or wasteful for the dozens we were not. The loader strategy gave us the same perceived speed without firing requests on every hover.

Prefetching What’s Likely Next

For tables, I added a row intersection observer that tracks which rows are visible. When a row enters the viewport, the observer kicks off a background queryClient.prefetchQuery() for that row’s detail view. By the time the user clicks, the detail data is usually already cached.

The observer ran with a small positive rootMargin so prefetches started just before the row was fully in view, which gave the network a few hundred milliseconds of head start on slow connections. The threshold stayed at the default; partial visibility was a strong enough signal. A Set tracked which row IDs had already been prefetched in the current session, so scrolling back and forth did not refire requests for rows already in the cache.

This was a better fit than blanket page-level prefetching. Most users do not page through a table sequentially. They scan, scroll, and click on the one or two rows that catch their eye. Prefetching exactly those rows was both cheaper and more accurate than prefetching N+1 in either direction. It also degraded gracefully: if a user scrolled too fast for the observer to fire, the detail view fell back to the same loader-based fetch the rest of the app used.

What I Disabled

I turned off refetchOnWindowFocus globally. Stale times are tuned based on how frequently each type of data changes, so a focus event is the wrong trigger; data that should refresh on focus would refresh on its own stale boundary anyway, and data that should not is exactly what users see refetching every time they switch back to the tab. Disabling it eliminated the jarring full-page refresh that users experienced when returning to the dashboard.

refetchOnReconnect came off for the same reason. The retry strategy lives in stale times, not in event triggers.

retry defaulted to a small fixed number for mutations and to zero for queries that returned 4xx errors. A 401 or 404 is not a transient failure; retrying it just delays the error the user needs to see.
